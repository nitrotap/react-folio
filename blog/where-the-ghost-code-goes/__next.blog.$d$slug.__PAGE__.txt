<h2 id="the-bug-is-a-lesson-about-erasure">The bug is a lesson about erasure</h2>
<p>Everyone describes Verus the same way: you write specifications and proofs alongside your code, and they&#39;re erased before compilation so they cost nothing at runtime. That&#39;s true. It is also the kind of sentence you can nod at for a year without knowing anything.</p>
<p>Here is what erasure actually is. In <code>source/builtin_macros/src/syntax.rs</code>, when the <code>verus!</code> macro meets a <code>Ghost(...)</code> or <code>Tracked(...)</code> call, it emits one of three things:</p>
<ul>
<li>in the erased build, <code>Ghost::assume_new_fallback(|| unreachable!())</code> — the payload is gone, and the closure that would produce it is unreachable</li>
<li>inside ghost context, <code>Ghost::new(inner)</code> — still ghost, just wrapped</li>
<li>in exec context, <code>ghost_exec(...)</code> tagged <code>#[verifier::ghost_wrapper]</code></li>
</ul>
<p>Two wrappers, three modes, six generated paths. The bug was that the visitor rewrote the expression before anyone read the turbofish off the original path, so <code>::&lt;int&gt;</code> was simply dropped on the floor in all six. The fix extracts <code>PathArguments</code> first and interpolates it into each <code>quote_spanned!</code>. That&#39;s the whole patch.</p>
<p>What I took from it is that &quot;erased&quot; is not an abstraction over the compiler. It is a branch. And the erased branch is real code that has to typecheck like anything else — which is why dropping a type argument produced a Rust inference failure rather than a verification failure. The proof and the program are the same source file being expanded twice, differently.</p>

<h2 id="what-a-permission-buys-that-an-assertion-doesnt">What a permission buys that an assertion doesn&#39;t</h2>
<p>An assertion is a claim checked at a point. It says something was true there. It says nothing about whether anyone else also believes it, or whether it stays true two lines later.</p>
<p>A permission is a value. You have to be handed one, you can only hand it on to one place, and you get it back only if the callee returns it. Here&#39;s a real signature:</p>

You cannot conjure one, because it&#39;s <code>external_body</code> and holds a <code>NoCopy</code>. You cannot hold two for the same location, because handing yours away moves it. Exclusive access stops being a comment and becomes a thing you either have or don&#39;t.</p>
<p>The part I find genuinely clever is who checks this. Verus has a test where a tracked value is consumed in two consecutive <code>match</code> scrutinees, and the expected failure is asserted as a <em>Rust</em> error: <code>use of moved value: t</code>. The linearity of the proof is caught by the same ownership discipline that catches it in your executable code. The OOPSLA&#39;23 paper — <em>Verus: Verifying Rust Programs using Linear Ghost Types</em> — puts the mode system exactly there: specifications are not checked for linearity and borrowing, while executable code and proofs are. Proofs are held to the borrow checker. Specs are not, which is why they get to be freely copyable and total.</p>
<h2 id="two-ways-to-pay">Two ways to pay</h2>
<p>My permutation harness proves a Fisher–Yates shuffle is a bijection with <code>N = 4</code>. Four, because three symbolic swaps is what stays tractable. My PRNG harness is better — <code>let state: u64 = kani::any()</code> is genuinely every state, all 2^64 of them, because there&#39;s no loop to unwind. But the bijection proof is bounded, and the bound is a sentence I have to write down honestly every time I describe it.</p>
<p>That&#39;s Kani&#39;s price: bound the input space, then say the bound out loud. In exchange you get memory safety, overflow, and panic checks on an existing crate before you have written a single specification. It&#39;s a very good trade and I&#39;d make it again.</p>
<p>Verus charges somewhere else entirely. There&#39;s no bound. There&#39;s also no free lunch: to reason about a raw pointer you must thread a <code>PointsTo</code> through every function that touches it, and that threading is real work in real signatures that a reviewer has to read. You are not annotating a program. You are writing a second program in the type system, and the two have to agree.</p>
<p>Kani asks you to shrink the world until the solver can see all of it. Verus asks you to carry the proof with you. I&#39;ve paid the first price 72 times. I&#39;ve only read the invoice on the second one — but I&#39;ve now read it closely enough to have found a place where it was misprinted, and that&#39;s a different kind of reading than skimming the docs.</p>
