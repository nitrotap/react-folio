1e:T4ad0,<p>Payload CMS ships with authentication. You put <code>auth: true</code> on a collection and you get email and password, sessions, and an admin panel that knows who is looking at it. It works, and for a lot of projects that is the end of the conversation.</p>
<p>Then somebody wants Google login. Or SSO against a corporate directory. Or MFA. So you reach for Auth0, and now two systems have an opinion about who a user is.</p>
<p>Everything hard about this integration follows from that sentence. The code does not.</p>
<h2 id="the-small-part">The small part</h2>
<p>Payload lets you replace the default strategy with your own. The whole contract is a <code>name</code> and an <code>authenticate</code> function that returns a user or null.</p>
<p>The security boundary is upstream of it, in token verification:</p>

<p>Three arguments there are load-bearing and all three are easy to get wrong quietly. Pinning <code>algorithms: [&#39;RS256&#39;]</code> is what stops a token from telling you how to verify it. Omit any one and verification still succeeds on the happy path, which is the problem.</p>
<p>That is the part I would not improvise. It is also about twenty lines, and it is the same twenty lines in every project.</p>
<h2 id="the-seam">The seam</h2>
<p>The interesting question is what happens on the line after <code>verifyAuth0Token</code> returns.</p>
<p>The token is valid. It carries a <code>sub</code> — an Auth0 user id like <code>auth0|123456</code>. Payload has never heard of it. What now?</p>

<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">  const</span><span style="--shiki-light:#005CC5;--shiki-dark:#79B8FF"> userInfo</span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583"> =</span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583"> await</span><span style="--shiki-light:#6F42C1;--shiki-dark:#B392F0"> getUserInfoFromAuth0</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">(token);</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">  user </span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">=</span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583"> await</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8"> payload.</span><span style="--shiki-light:#6F42C1;--shiki-dark:#B392F0">create</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">({</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">    collection: </span><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF">'users'</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">,</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">    data: {</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">      email: email </span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">||</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8"> userInfo.email,</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">      auth0Id: auth0UserId,</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">      name: userInfo.name,</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">      picture: userInfo.picture,</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">      emailVerified: userInfo.email_verified,</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">    },</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">  });</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">  return</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8"> { user, responseHeaders: </span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">new</span><span style="--shiki-light:#6F42C1;--shiki-dark:#B392F0"> Headers</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">() };</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">}</span></span></code></pre><p>Find or create, inside <code>authenticate</code>. It is the obvious implementation and it is worth being clear-eyed about what it means: authentication is now a write path. Any request bearing a valid token for an identity you have never seen will insert a row, before any of your access-control rules have run. Provisioning policy — who is allowed to become a user here — has to live in the token, because there is nowhere else for it to live by then.</p>
<p>Note also the join key. <code>auth0Id</code>, declared <code>unique: true</code>, <code>index: true</code>, <code>readOnly</code> in the admin UI. Not email. Email is a claim about a person that changes; <code>sub</code> is an opaque identifier that does not. Every system I have seen key on email eventually meets someone who changed theirs.</p>
<p>Once you write that block, the Payload user document has stopped being the source of truth about identity. It is a local projection of an Auth0 identity, keyed on <code>sub</code>, populated on first sight. A cache.</p>
<h2 id="two-mechanisms-for-the-same-job">Two mechanisms for the same job</h2>
<p>Which is fine — right up until you add the second way to fill it.</p>
<p>The guide also sets up an Auth0 webhook receiver that handles <code>user.created</code>, <code>user.updated</code>, and <code>user.deleted</code>, verifying an HMAC-SHA256 signature against <code>AUTH0_WEBHOOK_SECRET</code> and then doing <code>payload.create</code>, <code>payload.update</code>, and <code>payload.delete</code> against the same collection, matched on the same <code>auth0Id</code>.</p>
<p>Now the same three rows can be written by two independent mechanisms with different triggers and no ordering between them.</p>
<p>The <code>user.deleted</code> case is the one to sit with. The webhook deletes the Payload document. The strategy re-creates it on the next request that arrives with a still-valid access token, because from <code>authenticate</code>&#39;s point of view that is simply an identity it has not seen before. Access tokens outlive the delete. So does the row.</p>
<p>I would pick one. Webhook sync gives you a directory that stays current for users who never log in, which matters if editors need to be listed before their first visit. Just-in-time provisioning gives you a table that only contains people who actually showed up. Both are defensible. Running both means the reconciliation logic exists whether or not anyone wrote it.</p>
<p>The same duplication shows up again with roles. There is a <code>roles</code> select field on the Payload collection with <code>defaultValue: [&#39;user&#39;]</code>, and separately an Auth0 rule that stamps roles into the id token under a namespaced claim:</p>
<pre class="shiki shiki-themes github-light github-dark" style="--shiki-light:#24292e;--shiki-dark:#e1e4e8;--shiki-light-bg:#fff;--shiki-dark-bg:#24292e" tabindex="0"><code><span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">context.idToken[namespace </span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">+</span><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF"> '/roles'</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">] </span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">=</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8"> user.app_metadata?.roles </span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">||</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8"> [</span><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF">'user'</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">];</span></span></code></pre><p>Payload&#39;s access functions then read <code>user?.roles</code>. If those roles came from the local document, Auth0&#39;s copy is decoration. If they came from the token, the Payload field is a stale mirror that an admin can edit to no effect. Deciding which is a five-minute conversation that is very unpleasant to have a year later.</p>
<h2 id="the-one-i-would-change-before-shipping">The one I would change before shipping</h2>
<p>The callback route exchanges the authorization code and then hands the tokens back to the browser like this:</p>
<pre class="shiki shiki-themes github-light github-dark" style="--shiki-light:#24292e;--shiki-dark:#e1e4e8;--shiki-light-bg:#fff;--shiki-dark-bg:#24292e" tabindex="0"><code><span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">const</span><span style="--shiki-light:#005CC5;--shiki-dark:#79B8FF"> redirectUrl</span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583"> =</span><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF"> `${</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">process</span><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF">.</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">env</span><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF">.</span><span style="--shiki-light:#005CC5;--shiki-dark:#79B8FF">FRONTEND_URL</span><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF">}/auth/success?`</span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583"> +</span></span>
<span class="line"><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF">  `access_token=${</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">access_token</span><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF">}&#x26;`</span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583"> +</span></span>
<span class="line"><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF">  `id_token=${</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">id_token</span><span style="--shiki-light:#032F62;--shiki-dark:#9ECBFF">}`</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">;</span></span>
<span class="line"><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">res.</span><span style="--shiki-light:#6F42C1;--shiki-dark:#B392F0">redirect</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8">(redirectUrl);</span></span></code></pre><p>The React client picks them out of <code>window.location.search</code> and puts them in <code>localStorage</code>.</p>
<p>Query-string tokens end up in browser history, in server access logs, and in the <code>Referer</code> header of whatever the page loads next. The correct version is in the same document, a few sections down under security best practices — set an HTTP-only, <code>secure</code>, <code>sameSite: &#39;strict&#39;</code> cookie in the callback and redirect to a path with nothing in the URL. That section also says, in as many words, not to keep tokens in <code>localStorage</code> if you are worried about XSS.</p>
<p>Both halves are right there. The demo does the convenient thing and the guidance does the correct thing, which is how almost every auth integration I have read is written, including ones running in production.</p>
<h2 id="what-this-is-really-about">What this is really about</h2>
<p>The strategy is forty lines. The token verification is twenty and they are the same twenty everywhere. There is no clever part.</p>
<p>What there is, is a set of small decisions about where a fact is allowed to live: identity keyed on <code>sub</code> and nowhere else, roles in exactly one store, provisioning through exactly one path, tokens in exactly one place that is not a URL. Each is cheap to make on day one and expensive to discover on day four hundred, because by then both copies exist and both have users behind them.</p>
<p>That is the same instinct as putting a taxonomy in one file and generating the rest. Not because the code is hard. Because the invariant is easy to state and expensive to lose.</p>
