4:T2996,<p>There is a bug I kept thinking about while writing a resampling module.</p>
<p>A permutation test shuffles labels and recomputes a statistic. The shuffle has to be a genuine permutation — every index appearing exactly once. If it isn&#39;t, nothing crashes. No assertion fires. You get p-values that are subtly, quietly wrong, and you find out months later when a result won&#39;t replicate.</p>
<p>A unit test doesn&#39;t help much here. You can shuffle a thousand arrays and check each one, and you have learned something about a thousand arrays. The property you actually want is about <em>all</em> of them.</p>
<h2 id="what-model-checking-buys-you">What model checking buys you</h2>
<p>Kani is a bounded model checker for Rust. You write a harness that says &quot;for any input in this space, this must hold,&quot; and it either proves it or hands you a counterexample. Not a failing case it happened to sample — a constructed witness.</p>

Bounded model checking is bounded. But index-arithmetic bugs essentially always show up in small cases — off-by-one at the boundary, a swap that reads before it writes — and a proof over every arrangement of six elements is a stronger statement than a thousand random draws of a hundred.</p>
<h2 id="what-ended-up-under-proof">What ended up under proof</h2>
<p>The suite is 72 harnesses across 44 files. A few that earned their place:</p>
<ul>
<li><code>resampling_kfold_test_sets_partition</code> — k-fold test sets partition the dataset. No sample held out twice, none silently dropped. This is the one I&#39;d most expect to rot during a refactor.</li>
<li><code>moments_variance_non_negative</code> — Welford&#39;s online update can&#39;t produce a negative variance. It&#39;s a subtraction of accumulated quantities, and a naive implementation absolutely can go negative through cancellation.</li>
<li><code>p2_positions_strictly_increasing</code> — the P² quantile estimator maintains five markers that must stay ordered. The whole algorithm is meaningless if they cross.</li>
<li><code>rng_next_f64_in_unit_interval</code> — generated floats land in <code>[0, 1)</code>. The half-open interval is load-bearing; a <code>1.0</code> escaping into an inverse-CDF call produces an infinity.</li>
<li><code>ziggurat_table_indices_in_bounds</code> — the ziggurat sampler&#39;s table lookups stay in range for every candidate it generates.</li>
</ul>
<p>None of these are exotic. They&#39;re the things you&#39;d assert in a code review and then never check again.</p>
<h2 id="where-it-sits-in-the-build">Where it sits in the build</h2>
<p>The harnesses live in <code>#[cfg(kani)] mod verification</code> blocks next to the code they constrain. The <code>kani</code> cfg is registered in the workspace lints, so ordinary builds don&#39;t see them and don&#39;t pay for them. The crate keeps its zero-runtime-dependency guarantee — Kani never appears in <code>[dependencies]</code>.</p>
<p>The full suite takes north of twenty minutes, which is too slow for a pre-commit hook and fine for a release gate. That&#39;s where it runs.</p>
<p>Miri covers what Kani can&#39;t. Model checking reasons about a bounded input space; Miri executes the real test suite under an interpreter that detects undefined behaviour. Different tools, different blind spots.</p>
<p>And underneath both, the numbers still get checked empirically — every distribution, test, and estimator validated against <code>scipy.stats</code>, <code>scikit-learn</code>, <code>ruptures</code>, and <code>mlxtend</code> via committed golden fixtures, to tolerances between 1e-8 and 1e-12. Proof establishes structure. It does not tell you your incomplete gamma function is correct.</p>
<h2 id="the-part-i-didnt-expect">The part I didn&#39;t expect</h2>
<p>The most useful artefact wasn&#39;t a proof. It was a test called <code>gates.rs</code> that walks the source tree and fails the build if any <code>unsafe</code> block lacks a <code>// SAFETY:</code> justification on one of the three preceding lines.</p>
<p>The codebase contains no <code>unsafe</code> at all. The gate has never caught anything. It exists so that the day someone relaxes the lint for a SIMD path, the justification is not optional — the invariant is enforced by the build rather than by whoever reviews the PR.</p>
<p>That&#39;s the same instinct as the proofs, just cheaper. Most of what goes wrong in a codebase goes wrong because a rule lived in someone&#39;s head instead of in the build.</p>
