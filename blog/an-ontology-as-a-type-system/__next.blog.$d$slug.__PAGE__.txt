4:T181a,<p>Every statistics library eventually invents a taxonomy. Some distributions are continuous, some discrete. Some have a mean, some famously don&#39;t. Some tests are parametric, some aren&#39;t; some return an effect size and some have no defined one.</p>
<p>That taxonomy usually lives in three places at once: partially in the trait hierarchy, partially in the docs, and mostly in the head of whoever wrote it. The three drift.</p>
<p>So I put it in one place and generated the rest.</p>
<h2 id="the-shape">The shape</h2>
<p>The <code>ds</code> ontology is a TypeDB namespace — entities, attributes, relations, and the subtyping between them. It is the source of truth. A generator with no dependencies outside <code>std</code> reads it and emits the Rust type layer:</p>
<pre class="shiki shiki-themes github-light github-dark" style="--shiki-light:#24292e;--shiki-dark:#e1e4e8;--shiki-light-bg:#fff;--shiki-dark-bg:#24292e" tabindex="0"><code><span class="line"><span>ds ontology (TQL)  ──gen-ontology──▶  src/generated.rs  ──▶  hand-written math</span></span>
<span class="line"><span>  entities/attrs                       15 traits              (src/math.rs, …)</span></span>
<span class="line"><span>  relations/functions                  140 structs</span></span></code></pre><p>Two rules do most of the work:</p>
<p><strong>Abstract entities become marker traits, with the hierarchy preserved.</strong> If the ontology says a normal distribution is a <code>Distribution</code>, which is a <code>StatisticalConstruct</code>, which is an <code>AbstractEntity</code>, the generated Rust says exactly that:</p>
<pre class="shiki shiki-themes github-light github-dark" style="--shiki-light:#24292e;--shiki-dark:#e1e4e8;--shiki-light-bg:#fff;--shiki-dark-bg:#24292e" tabindex="0"><code><span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">pub</span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583"> trait</span><span style="--shiki-light:#6F42C1;--shiki-dark:#B392F0"> Distribution</span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">:</span><span style="--shiki-light:#6F42C1;--shiki-dark:#B392F0"> StatisticalConstruct</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8"> {}</span></span>
<span class="line"><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">pub</span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583"> trait</span><span style="--shiki-light:#6F42C1;--shiki-dark:#B392F0"> StatisticalConstruct</span><span style="--shiki-light:#D73A49;--shiki-dark:#F97583">:</span><span style="--shiki-light:#6F42C1;--shiki-dark:#B392F0"> AbstractEntity</span><span style="--shiki-light:#24292E;--shiki-dark:#E1E4E8"> {}</span></span></code></pre><p><strong>Concrete entities become structs</strong> carrying every inherited attribute and implementing every ancestor trait. Add an attribute to a parent in the ontology and it appears on every descendant struct on the next generation, or the build breaks. There is no version of this where the docs and the types disagree, because the docs aren&#39;t the source — the ontology is.</p>
<p>There&#39;s a second grouping layer that turned out to matter more than expected: domain grouping by subtyping (statistics vs. machine learning), and <em>intent</em> grouping by relation. Intent is the thing a user actually arrives with — &quot;find the communities,&quot; &quot;test whether these differ&quot; — and it cuts across the type hierarchy. A relation expresses that without contorting the subtyping.</p>
<h2 id="what-is-not-generated">What is not generated</h2>
<p>The numerics. All of them.</p>
<p>The generated types are skeletons — parameter structs, trait impls, the shape of the thing. Every incomplete gamma function, every exact p-value, every ziggurat table is written by hand against those skeletons.</p>
<p>This is the part I&#39;d defend hardest. Generating a type layer from a schema is a well-understood trade: you accept a build step and you get a guarantee that the taxonomy is internally consistent. Generating <em>numerical methods</em> is a different proposition entirely, and the failure mode is silent wrongness in the fourth decimal place. The line sits exactly where the interesting judgement starts.</p>
<h2 id="carving-a-public-crate-out-of-it">Carving a public crate out of it</h2>
<p>The workspace is large and most of it isn&#39;t ready to be public API. The published <code>stats-claw</code> crate is carved out of it mechanically, driven by a config file rather than by copying:</p>
<pre class="shiki shiki-themes github-light github-dark" style="--shiki-light:#24292e;--shiki-dark:#e1e4e8;--shiki-light-bg:#fff;--shiki-dark-bg:#24292e" tabindex="0"><code><span class="line"><span>include_family = StatisticalConstruct</span></span>
<span class="line"><span>include_family = LearningConstruct</span></span>
<span class="line"><span>exclude_family = Intent</span></span>
<span class="line"><span>exclude_family = Theorem</span></span>
<span class="line"><span>exclude_family = ComputationalMethod</span></span></code></pre><p>The carve decides what ships by walking the same ontology the types came from. Families that represent internal composition or theory layers never leave the workspace. Because the rule is expressed against the ontology and not against file paths, adding a new entity puts it on the correct side of the boundary automatically.</p>
<p>A second ontology would carve with only a profile change — no family name, namespace, or path is baked into the tool.</p>
<h2 id="was-it-worth-it">Was it worth it</h2>
<p>For a library this size, honestly: the generator took longer than hand-writing 140 structs would have.</p>
<p>What it bought is that the taxonomy can now be <em>wrong in exactly one place</em>. When I decided that a result type belonged under a different family, that was a one-line ontology edit and a regeneration, not an afternoon of grepping for every place the old assumption had been written down.</p>
<p>That&#39;s the same reason the proofs exist. Not because the code is hard, but because the invariants are easy to state and expensive to lose.</p>
