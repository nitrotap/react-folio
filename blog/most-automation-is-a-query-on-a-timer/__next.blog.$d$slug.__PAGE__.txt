4:T205a,<p>Automation rules in Jira and Confluence have one shape: <strong>Trigger → Condition(s) → Action(s)</strong>. Something happens, you check whether it matters, you do something about it.</p>
<p>I keep notes on the rules worth keeping. Going back through the Jira ones, four out of five had the same trigger.</p>
<pre class="shiki shiki-themes github-light github-dark" style="--shiki-light:#24292e;--shiki-dark:#e1e4e8;--shiki-light-bg:#fff;--shiki-dark-bg:#24292e" tabindex="0"><code><span class="line"><span>Trigger: Scheduled (daily at 9 AM)</span></span>
<span class="line"><span>Condition: JQL Query</span></span>
<span class="line"><span>JQL: priority = Critical AND status not in (Done, Closed) AND updated &#x3C;= -2d</span></span>
<span class="line"><span>Action: Send email to project lead</span></span></code></pre><p>That is not event-driven anything. It is a saved search on a cron. The trigger carries no information — a clock ticked. Every bit of logic in the rule lives in one line of JQL, and the action is a single call at the end.</p>
<p>Same for auto-closing resolved issues, <code>status = Resolved AND updated &lt;= -7d AND resolution is not EMPTY</code>. Same for sprint cleanup, <code>Sprint in openSprints() AND status = &quot;To Do&quot; AND assignee is EMPTY AND created &lt;= -3d</code>. Same for code review nags, <code>status = &quot;Code Review&quot; AND updated &lt;= -2d AND assignee in membersOf(&quot;developers&quot;)</code>.</p>
<p>Once you see it, the rule builder starts looking like the wrong mental model. You&#39;re not writing a workflow. You&#39;re writing a query and choosing how often to run it.</p>
<h2 id="why-the-scheduled-version-is-usually-the-right-one">Why the scheduled version is usually the right one</h2>
<p>The obvious objection is latency. An event trigger fires the moment an issue is created; a daily schedule fires up to twenty-four hours late. If you genuinely need the response now, use the event.</p>
<p>Most of the time you don&#39;t, and you get three things back for the delay.</p>
<p><strong>A scheduled rule cannot recurse.</strong> This is the big one. The standard advice about automation is to be careful with rules that modify the same fields they monitor, use conditions to prevent recursive execution, and consider rule execution order. Which is correct, and worth noticing what kind of advice it is: nothing in the system checks any of it. There is no type checker for &quot;this Edit Issue action re-triggers the Issue Updated rule that produced it.&quot; The only thing standing between you and a loop is a condition you remembered to write, in a rule someone else may edit next quarter. A clock-triggered rule has no such failure mode. It runs N times a day regardless of what it does.</p>
<p><strong>A scheduled rule has a knowable cost.</strong> Jira Cloud allows 1000 rules per site and 100 executions per rule per month, varying by plan; Confluence Cloud is 1000 rules per site with plan-based execution limits. Server and Data Center have no built-in limits, but performance considerations still apply. A daily rule costs about thirty executions a month and you know that before you deploy it. An <code>Issue Updated</code> rule costs whatever your team happens to do in October.</p>
<p><strong>A scheduled rule is readable.</strong> The JQL is the whole specification. You can paste it into the issue navigator and see exactly the set the rule will act on, right now, before it acts on anything. There is no equivalent for &quot;what would this event rule have done last Tuesday.&quot;</p>
<h2 id="the-query-is-the-program">The query is the program</h2>
<p>Which makes the query language the thing actually worth learning, and JQL is more expressive than most people who use it daily realise.</p>
<p>It has history, not just state:</p>
<pre><code>status changed from "To Do" to "In Progress" by currentUser()
status changed to "Done" during (-1w, now())
assignee changed after "-2d"</code></pre><p>It has agile-aware functions that resolve against live board state:</p>
<pre><code>Sprint in openSprints()
Sprint in closedSprints() AND Sprint not in futureSprints()
fixVersion in unreleasedVersions()</code></pre><p>It has group membership, so a rule can target a role rather than a list of names that goes stale — <code>assignee in membersOf(&quot;jira-developers&quot;)</code>, <code>reporter in membersOf(&quot;developers&quot;)</code>. And it has relative dates everywhere, which is what makes staleness expressible at all: <code>updated &lt;= -7d</code>, <code>created &lt;= endOfMonth(-1)</code>, <code>created &gt;= startOfYear()</code>.</p>
<p>Put those together and a rule like &quot;in-progress work nobody has touched in a week&quot; is one clause, <code>status = &quot;In Progress&quot; AND updated &lt;= -1w AND assignee != EMPTY</code>, and it will still mean the same thing in two years.</p>
<p>CQL on the Confluence side is the same idea with different nouns. <code>space = &quot;DOCS&quot; AND lastmodified &lt;= -90d AND status = current AND type = page</code> is a documentation review queue. <code>label is null AND space = &quot;PROJ&quot; AND type = page</code> finds content nobody categorised. <code>ancestor = &quot;Meeting Notes&quot; AND created &gt;= startOfMonth()</code> walks the page tree. Text matching supports wildcards and quoted exact phrases, <code>title ~ &quot;ADR*&quot;</code> and <code>text ~ &quot;\&quot;exact phrase\&quot;&quot;</code>.</p>
<p>Neither language has variables, functions, or a way to be tested. That&#39;s the ceiling, and it&#39;s a low one. It&#39;s also why the discipline of keeping the logic inside the query is worth something: an expression you can&#39;t unit-test should at least be an expression you can read in one line and run by hand.</p>
<h2 id="where-rules-stop-being-queries">Where rules stop being queries</h2>
<p>Two features push past that ceiling and both deserve suspicion in proportion to how useful they are.</p>
<p>Smart values interpolate context into actions — <code>{{issue.key}}</code>, <code>{{issue.assignee.displayName}}</code>, <code>{{trigger.changelog.field}}</code>, <code>{{now}}</code>, and <code>{{#issues}}...{{/issues}}</code> to iterate. Branching adds control flow:</p>
<pre class="shiki shiki-themes github-light github-dark" style="--shiki-light:#24292e;--shiki-dark:#e1e4e8;--shiki-light-bg:#fff;--shiki-dark-bg:#24292e" tabindex="0"><code><span class="line"><span>{{#if(equals(issue.priority,"Critical"))}}</span></span>
<span class="line"><span>Send immediate alert</span></span>
<span class="line"><span>{{else}}</span></span>
<span class="line"><span>Add to daily digest</span></span>
<span class="line"><span>{{/if}}</span></span></code></pre><p>That is a template language with conditionals, living in a text box, with no version control and no test harness. It is genuinely the right tool for formatting a Slack message. It is the wrong place to put a business rule, because the moment a branch means something, the rule has become a program that nobody can review as one.</p>
<p>The other thing worth naming: rules execute as somebody. The standing guidance is to grant automation permissions carefully, use service accounts for rule execution, and audit permissions regularly — because a rule inherits an identity, and a rule holding admin permissions is an admin that never sleeps and never asks. <code>Delete Issue</code> is an available action. So is <code>Execute Script</code>.</p>
<h2 id="what-id-actually-do">What I&#39;d actually do</h2>
<p>Write the JQL first, in the issue navigator, and look at what comes back. If the result set is right, you have most of a rule. If it isn&#39;t, you have saved yourself deploying something that quietly acts on the wrong hundred issues.</p>
<p>Prefer a schedule unless latency genuinely matters. Keep one purpose per rule and name it after what it does, not after what triggered it. Put the logic in the query and leave the action dumb.</p>
<p>And when the temptation arrives to add a branch, a smart-value template, and a second condition group to one rule — that&#39;s the signal that the thing you&#39;re building stopped being automation and became software, and it should go somewhere software can be reviewed.</p>
