It&#39;s a plausible-looking call to something real — a refund issued, a row deleted, an outbound request to a host nobody meant to be reachable. The model picked the tool at runtime. There was no branch in my code that decided it.</p>
<p>That&#39;s an awkward place to stand if your instinct is to prove things. There&#39;s no invariant to state. &quot;The agent calls the right tool&quot; isn&#39;t a property of a program; it&#39;s a property of a distribution over a prompt you haven&#39;t seen yet.</p>
<p>So I read the documentation for Google&#39;s Agent Gateway with one question in mind: of everything that can go wrong at that boundary, how much can a network control point actually catch?</p>
<p>I haven&#39;t deployed it. This is a docs read.</p>
<h2 id="what-it-is">What it is</h2>
<p>Agent Gateway is described as the networking component of the Gemini Enterprise Agent Platform — it secures and governs connectivity for agentic interactions, whether between users and agents, agents and tools, or agents and each other. It runs in one of two modes. <code>CLIENT_TO_AGENT</code> is ingress: clients reaching your hosted agents. <code>AGENT_TO_ANYWHERE</code> is egress: your agent reaching out to MCP servers, other agents, and API endpoints.</p>
<p>Egress is the interesting one, and its central mechanic is an allowlist. Resources get registered in Agent Registry — agents, MCP servers, tools, endpoints — and the docs are blunt about the consequence: registering them is required, because the gateway blocks all outbound traffic to hosts not in the registry. Anything unregistered is denied by default.</p>
<p>That&#39;s a real property. It&#39;s decidable, it holds for every request, and it doesn&#39;t depend on anything the model said. Same for identity: agent identities are secured by default with Context-Aware Access, using mTLS and DPoP, and the gateway uses that identity as the principal for authorization. IAM allow and deny policies then restrict which agent may reach which tool, with conditions expressible over attributes of the call — the resource name, whether the operation is read-only, whether it&#39;s destructive, whether it&#39;s idempotent.</p>
<p>I&#39;d call that layer enforcement in the strict sense. It&#39;s a predicate over the request, evaluated the same way every time, and if it says no the call does not happen.</p>
<h2 id="the-part-that-is-a-grader">The part that is a grader</h2>
<p>Then there&#39;s Semantic Governance. You write constraints in natural language — up to 5,000 characters — scoped to an agent or to a specific tool. The docs&#39; own example is a shipping rule: always use UPS within the USA, always DHL within the EU. A policy engine evaluates each proposed tool call against the current user prompt, the constraints, the tools manifest, the chat history, and the suggested invocations, and returns <code>ALLOW</code> or <code>DENY</code>.</p>
<p>That is an LLM judge sitting in the request path.</p>
<p>The documentation says so, in a warning I did not expect to find and respect for being there: Semantic Governance Policy is a generative AI service that uses an LLM to implement natural language policies; LLMs are probabilistic and can make mistakes; verdicts may not be accurate.</p>
<p>I&#39;ve built graders — harness-level evaluators that score model output for hallucination, run offline against a fixed set. The technology here is the same. The position is not. Offline, a grader&#39;s errors cost you a slightly wrong number in a report. Inline, its false negatives are your security posture and its false positives are an outage. A grader promoted to an enforcement point inherits obligations it was never measured against.</p>
<p>Which is presumably why every path through these docs routes you through dry-run first.</p>

The verdict logs carry a rationale field, so the corpus arrives annotated.</p>
<p>And <code>failOpen: true</code>, at a one-second timeout. If the authorization extension doesn&#39;t answer, traffic proceeds. That&#39;s a defensible availability default and it is also the precise difference between a control and a guarantee. A proof does not have a timeout.</p>
<h2 id="where-the-line-falls">Where the line falls</h2>
<p>The gateway sees requests. That&#39;s its vantage point and its ceiling.</p>
<p>It can tell you an agent called <code>process_refund</code>. It cannot tell you the refund was owed. It can confirm the destination was registered and the identity was permitted and the method was not marked destructive. It cannot confirm the reasoning that produced the call was sound, because that reasoning never crosses the network boundary — only its output does. Everything the gateway knows about intent, it knows by asking another model.</p>
<p>The structural limits are stated plainly too. HTTP-based traffic only, including MCP and A2A — so an MCP server your agent speaks to over stdio is simply not in scope. No VPC Service Controls. No self-signed certificates. A cap of 5,000 registered resources per gateway, and at most four custom authorization policies on an egress gateway. And the default-deny is only as strong as registry hygiene: the perimeter is exactly the set of things somebody remembered to register, which makes the registry an operational artefact with security consequences rather than an inventory.</p>
<p>None of this is a criticism. It&#39;s the shape of the tool. I&#39;ve spent enough time writing Kani harnesses for index arithmetic to know how narrow the provable region is — a permutation is a bijection, a variance is non-negative, a float lands in <code>[0, 1)</code>. Those are properties you can close over all inputs. &quot;This tool call served the user&#39;s actual intent&quot; is not in that family and never will be.</p>
<p>What&#39;s left is a layered answer. Prove what&#39;s provable. Enforce what&#39;s decidable — registry membership, identity, IAM conditions on the call itself. Measure everything above that, honestly, with the enforcement turned off until the measurement says something.</p>
<p>The thing I&#39;d resist is the slide between those layers. A gateway is where you put the rules you can state but can&#39;t prove, and that&#39;s a genuinely useful place for them to live. It stops being useful the moment it gets described as making an agent safe. It makes an agent <em>governed</em>, which is a weaker and more honest claim, and the documentation — to its credit — mostly makes the weaker one.</p>
